# 设计门禁规则（HARD-GATE）

## 核心原则

**在设计被用户批准前，禁止：**
- 写任何实现代码
- 创建任何文件（设计文档除外）
- 执行任何构建命令
- 调用实现类 skill

## `<HARD-GATE>` 标记语义

`<HARD-GATE>` 是一个强制门禁标记，用于：
1. **声明阶段边界** — 明确标记某个 skill 必须完成的前置条件
2. **触发门禁检查** — 任何实现动作前必须通过门禁验证
3. **阻止越界行为** — 未通过门禁时立即停止并输出错误消息

### 门禁状态机

```
[用户请求]
    ↓
[检测实现意图?]
    ↓ Yes                    ↓ No
[检查设计批准文件]      [继续正常流程]
    ↓
[存在有效批准?]
    ↓ Yes         ↓ No
[通过门禁]    [输出 HARD-GATE 警告]
    ↓                   ↓
[允许实现]    [等待设计完成 + 批准]
```

## 门禁检查点

### 1. 需求澄清阶段
- brainstorming skill 完成
- 用户意图已明确
- 范围已界定

### 2. 设计方案阶段
- 设计文档已写入 `docs/plans/YYYY-MM-DD-<topic>-design.md`
- 2-3 种方案已评估
- 推荐方案已说明
- 设计文档经 `document-review` 系统审查（类型化检查：完整性/一致性/边界/依赖）

### 3. 用户批准阶段
- 用户明确批准设计（口头或书面）
- `.claude/.design-approved` 文件已创建
- 批准时间戳已记录

### 4. 实现计划阶段
- writing-plans skill 生成任务列表
- WU 已分解
- 审查者已分配

## 批准文件格式

**位置：** `.claude/.design-approved`

**格式：**
```json
{
  "status": "approved",
  "timestamp": "2026-07-02T10:00:00Z",
  "approved_by": "user",
  "design_path": "docs/plans/2026-07-02-feature-design.md",
  "expires_at": "2026-07-03T10:00:00Z",
  "scope": {
    "features": ["feature-1", "feature-2"],
    "excluded": ["out-of-scope-feature"]
  }
}
```

**有效窗口：** 批准后 24 小时内可实现

## 违规处理流程

### 检测到违规时：

1. **立即停止** — 停止当前所有动作
2. **输出警告** — 显示 `[HARD-GATE]` 错误消息
3. **列出步骤** — 说明需要完成的设计步骤
4. **等待确认** — 不继续执行直到门禁通过

### 错误消息模板

```
[HARD-GATE] 设计门禁未通过

检测到：您在设计被批准前尝试执行实现操作。

当前状态：
- brainstorming: ✓ 完成 / ✗ 未开始
- 设计文档: ✓ 已写 / ✗ 不存在
- 用户批准: ✓ 已批准 / ✗ 未批准

下一步：
1. 完成 brainstorming（如果未开始）
2. 编写设计文档到 docs/plans/
3. 提交给用户审查并获得批准
4. 创建 .claude/.design-approved 文件

当前设计阶段请使用 brainstorming skill。
```

## 例外情况

以下情况可以跳过设计门禁：

### 1. quick-fix（小改动）
用户明确说是"小改动"、"quick fix"、"直接改"时：
- 已有明确的 bug 定位
- 改动范围 ≤ 5 行代码
- 不涉及架构变更

### 2. 用户明确授权
用户说"直接实现"、"不用设计了"、"开始写代码"时：
- 用户已理解风险
- 跳过是用户主动决策
- 记录在会话中

### 3. 单行配置变更
环境变量、简单配置调整：
- 不涉及业务逻辑
- 不需要设计评审
- 可回滚

### 4. 测试文件
单元测试、集成测试：
- 基于已有实现
- 不改变业务逻辑
- 可独立验证

## 门禁豁免标记

在极少数情况下，可以使用豁免标记：

```markdown
<!-- HARD-GATE-EXEMPT: user-authorized-quick-fix -->
```

**使用条件：**
- 用户明确口头或书面授权
- 豁免原因必须记录
- 事后需补充设计文档（如果复杂度增加）

## 实施检查清单

### 实现前必须确认：
- [ ] brainstorming 已完成
- [ ] 设计文档已写入 `docs/plans/`
- [ ] 用户已审查设计
- [ ] 用户已明确批准（`.claude/.design-approved` 存在）
- [ ] 实现计划（writing-plans）已生成

### 实现中必须遵守：
- [ ] 只实现设计范围内的功能
- [ ] 如需变更设计，先更新设计文档并重新批准
- [ ] 保持与设计文档的同步

### 实现后：
- [ ] 代码符合设计意图
- [ ] 通过两阶段审查（spec 合规 + 代码质量）
