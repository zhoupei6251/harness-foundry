# 两阶段审查协议

> 审查分为两个独立阶段：Spec 合规 → 代码质量。分离关注点，确保实现既满足设计又具备高质量。

## 概述

### 为什么分两阶段？

| 问题 | 单一审查 | 两阶段审查 |
|------|----------|------------|
| 设计偏离 vs 代码问题 | 混在一起 | 分开处理 |
| 返修焦点 | 全部返修 | 按阶段精准返修 |
| 审查者精力 | 分散 | 各司其职 |
| 通过率追踪 | 模糊 | 清晰 |

### 核心原则

1. **阶段 1 通过前，阶段 2 不会开始**
2. **每阶段最多 2 次返修**
3. **返修只针对失败的阶段**
4. **2 次返修仍失败 → 报告用户介入**

---

## 阶段 1: Spec 合规审查

### 目的

验证实现是否**严格遵循**批准的设计文档。

### 执行者

`spec-compliance-reviewer` agent

### 检查项

- [ ] 所有 done criteria 是否满足
- [ ] 是否有遗漏的功能点
- [ ] 实现是否偏离设计意图
- [ ] 边界情况是否处理
- [ ] 是否有设计外的功能混入

### 通过条件

**PASS**: 所有检查项通过

**PARTIAL**: 大部分满足，有少量遗漏或轻微偏离（可快速修复）

**FAIL**: 严重偏离设计，或大量遗漏

### 输出格式

```markdown
## Spec 合规审查报告

### 审查对象
- 设计文档: <path>
- 实现: <path>
- 时间: <timestamp>

### 结果: PASS | PARTIAL | FAIL

### 符合项
- <列表>

### 缺失项
- <描述>

### 偏离项
- <描述 + 建议修复方向>

### 阻塞问题
无 | <问题列表>

### 下一步
通过 | 返回给实现者返修
```

---

## 阶段 2: 代码质量审查

### 目的

验证代码本身是否**高质量**（不关注是否满足 spec，关注代码素质）。

### 执行者

`reviewer` agent（通用五轴审查）

### 检查项

| 轴 | 检查点 |
|---|--------|
| 正确性 | 逻辑是否正确，边界与错误路径处理 |
| 可读性 | 命名、控制流、注释、避免过度抽象 |
| 架构 | 遵循项目模式、模块边界清晰 |
| 安全 | 输入校验、密钥管理、注入风险 |
| 性能 | N+1、无界循环、热路径优化 |

### 通过条件

**APPROVE**: 无 Critical/Important 问题

**BLOCK**: 存在 Critical 或 Important 问题

### 输出格式

```markdown
## 代码质量审查报告

### 审查对象
- 变更文件: <列表>
- 时间: <timestamp>

### 结果: APPROVE | BLOCK

### Findings

#### Critical（阻塞，必须修复）
- <问题描述 + 证据>

#### Important（应修复）
- <问题描述 + 建议>

#### Suggestion/Nit（可选）
- <建议>

### 未验证项
- <无法从 diff 验证的项，需人工确认>

### 总体评估
<1-2 句技术评估>
```

## 执行顺序

```
实现完成
    ↓
阶段 1: Spec 合规审查
    ↓
[FAIL?] → 返修给 WU 实现者（最多 2 次）→ 重新阶段 1 审查
    ↓
[PARTIAL?] → 返修给 WU 实现者（可选）→ 重新阶段 1 审查
    ↓
[PASS]
    ↓
阶段 2: 代码质量审查
    ↓
[BLOCK?] → 返修给 WU 实现者（最多 2 次）→ 重新阶段 2 审查
    ↓
[APPROVE] → 完成
```

### 返修流程

1. Leader 解析审查报告，提取需修复项
2. 派发 `review-fix` WU 给原实现者（或新的 coder）
3. 修复完成后重新执行对应阶段的审查
4. 记录返修次数（最多 2 次）

### 2 次返修仍失败

```
最终报告: 包含所有阶段的审查结果 + 未解决的问题
状态: USER_INTERVENTION_REQUIRED
操作: 提示用户介入决策
```

## 示例流程

### 场景 1: 两阶段全部通过

```
阶段 1: PASS
阶段 2: APPROVE
结果: 完成
```

### 场景 2: 阶段 1 返修后通过

```
阶段 1: FAIL（遗漏 done criteria #3）
返修 1: 修复 done criteria #3
阶段 1: PASS
阶段 2: APPROVE
结果: 完成
```

### 场景 3: 阶段 2 返修后通过

```
阶段 1: PASS
阶段 2: BLOCK（Critical: 未处理空指针）
返修 1: 添加空指针检查
阶段 2: APPROVE
结果: 完成
```

### 场景 4: 超过 2 次返修

```
阶段 1: FAIL
返修 1: FAIL（仍有遗漏）
返修 2: FAIL（仍未通过）
最终报告: [阶段1状态] FAIL, [阶段2状态] N/A, 未解决问题: <列表>
结果: USER_INTERVENTION_REQUIRED
```

## 与 Superpowers 的对比

| 方面 | Superpowers | Harness Foundry（两阶段） |
|------|-------------|-------------------------|
| 审查粒度 | 每任务后一次（合并 spec+quality） | 每任务后两次（分离） |
| Spec 偏离处理 | 与质量检查混在一起 | 独立处理，更聚焦 |
| 返修循环 | 修复后重新审查 | 按阶段返修，更精准 |
| 角色分工 | task-reviewer（合并） | spec-compliance + reviewer（分离） |
| 报告格式 | 合并 verdicts | 独立报告 |

**两阶段的优势**：
- 分离关注点，审查者更专注
- 返修只针对失败的阶段，减少不必要的返修
- 通过率追踪更清晰

**Superpowers 的优势**：
- 一次审查覆盖两面，更高效
- 审查者可以综合判断

Harness Foundry 选择两阶段是为了**分离关注点**和**精准返修**。
